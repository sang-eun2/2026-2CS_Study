## 한눈에 보기
> 프로그래머가 믿는 추상화(정수, 실수, 메모리, 성능)에는 **경계**가 있다. 경계를 알려면 추상화 아래(비트, 어셈블리, 캐시)를 봐야 한다.

| 현실 | 예제 | 다시 나오는 주차 |
|---|---|---|
| #1 정수 ≠ 수학의 정수, 실수 ≠ 수학의 실수 | 50000² 오버플로, 부동소수점 덧셈 순서 | 2~4주 |
| #2 어셈블리를 알아야 한다 | 쓰진 않아도 읽어야 버그·성능·보안이 보인다 | 5~11주 |
| #3 메모리는 중요하다 | 배열 범위 밖 쓰기가 옆 변수를 망가뜨림 | 7, 9~11주 |
| #4 성능 ≠ 점근 복잡도 | 루프 순서만 바꿔 약 19배 차이 | 12~13주 |
| #5 컴퓨터는 실행 이상을 한다 | I/O, 네트워크 | 1주 Part 2, 14주 |

## 현실 #1: 유한한 표현
### 제곱이 음수가 될 수 있다
- 32비트 int 최댓값 = 2³¹ − 1 = **2,147,483,647**
- 40000² = 1,600,000,000 ✅, 50000² = 2,500,000,000 ❌ (범위 초과)
- 하위 32비트만 남기면 −1,794,967,296 이 되지만, **C 의 signed 오버플로는 정의되지 않은 동작(UB)** 이라 이 값을 보장하지 않는다
- 16비트 2의 보수에서는 32,767 다음 비트 패턴이 −32,768

### 부동소수점 덧셈은 결합 법칙이 깨진다
| 식 | 결과 | 이유 |
|---|---|---|
| (1e20 − 1e20) + 3.14 | **3.14** | 큰 수가 먼저 상쇄 |
| 1e20 + (−1e20 + 3.14) | **0** | −1e20 + 3.14 가 반올림되어 −1e20 이 됨 (double 유효숫자 약 15~16자리) |

### 자료형마다 다른 규칙 (덧셈 결합 법칙)
- **unsigned**: w 비트 연산은 2ʷ 로 나눈 나머지로 순환 → 결합 법칙 **성립**
- **signed int**: 모든 중간 결과가 범위 안일 때만 보장
- **부동소수점**: 범위 안에서도 반올림 때문에 깨질 수 있음

| 언어 | 숨겨 주는 것 | 대가 |
|---|---|---|
| Python | 메모리 관리, 타입 변환 | 무엇이 어떻게 실행되는지 안 보임 |
| C | (타입·메모리를 직접 다룸) | 할당·해제·크기 직접 구현 |
| 어셈블리 | 하드웨어 직접 제어 | 어렵고 이식성 낮음 |

> 이 수업의 위치: **C 로 쓰고 어셈블리로 읽는다.**

## 현실 #2: 어셈블리를 읽을 줄 알아야 한다
컴파일러가 더 잘 쓰므로 **쓰기가 아니라 읽기**를 배운다. 이유:
1. 버그가 있을 때 실제 동작 확인
2. 성능 튜닝 (컴파일러가 한/안 한 최적화)
3. 시스템 소프트웨어 구현 (컴파일러, OS)
4. 악성코드 분석·방어 (리버스 엔지니어링)

## 현실 #3: 메모리는 무한하지도, 안전하지도, 균일하지도 않다
### 배열 범위 밖 쓰기
```c
typedef struct { int a[2]; double d; } struct_t;
double fun(int i) {
    volatile struct_t s;
    s.d = 3.14;
    s.a[i] = 1073741824;   /* 2^30, 범위 밖일 수 있음 */
    return s.d;
}
```
| 호출 | 결과(예) | 이유 |
|---|---|---|
| fun(0), fun(1) | 3.14 | a[0], a[1] 정상 범위 |
| fun(2) | 3.1399998664856 | d 의 **하위 4바이트**를 덮어씀 → 가수 끝부분만 조금 바뀜 |
| fun(3) | 2.00000061035156 | d 의 **상위 4바이트**(부호·지수·가수 앞부분)를 덮어씀 → 값이 크게 바뀜 |
| fun(4), fun(5) | 3.14 | 구조체 밖이지만 스택 프레임 안 → **겉보기엔 정상 (더 위험)** |
| fun(6) | Segmentation fault | 반환 주소 같은 중요 상태 파괴 |

- C 는 **배열 범위를 검사하지 않는다** → 잘못된 쓰기가 옆 변수를 조용히 망가뜨림
- 결과는 컴파일러·환경마다 다르다 (정의되지 않은 동작)
- **volatile**: 컴파일러가 그 변수의 읽기·쓰기를 생략하지 못하게 함 (주로 하드웨어 레지스터, 임베디드). 범위 밖 접근을 안전하게 만들지는 않음
- **원격 작용(action at a distance)**: 망가진 객체와 접근한 객체가 무관, 증상이 한참 뒤에 나타남
- 대처: 자동 메모리 관리 언어 사용 / 상호작용 원리 이해(이 수업) / Valgrind, AddressSanitizer 같은 도구

### 용어 (가볍게)
- **세그먼트**: 가상 메모리를 목적별로 나눈 영역(코드·데이터·힙·스택). Segmentation fault = 허용되지 않은 영역 접근
- **스택 프레임**: 함수 호출 때 생기는 영역 (지역 변수, 인자, 반환 주소)

## 현실 #4: 성능은 Big-O 만으로 정해지지 않는다
```c
void copyij(int src[2048][2048], int dst[2048][2048]) {   // 행 방향
    for (i = 0; i < 2048; i++) for (j = 0; j < 2048; j++) dst[i][j] = src[i][j];
}
void copyji(...) {                                          // 열 방향
    for (j = 0; j < 2048; j++) for (i = 0; i < 2048; i++) dst[i][j] = src[i][j];
}
```
- copyij **4.3 ms** vs copyji **81.8 ms** → 약 **19배** (Haswell 2.0GHz 측정 예)
- 이유: C 배열은 **행 우선** 저장 → copyij 는 연속 접근으로 **공간 지역성**을 살려 캐시 적중률이 높고, copyji 는 2048칸씩 건너뛴다
- 최적화 수준: 알고리즘, 데이터 표현, 프로시저, 루프 + 메모리 접근 패턴, 캐시, ILP, 분기 예측

## 현실 #5: 컴퓨터는 프로그램 실행 이상의 일을 한다
- I/O 는 신뢰성과 성능에 결정적
- 네트워크: 동시성, 불안정한 매체(손실·지연), 플랫폼 간 호환성, 대역폭·지연·혼잡

## 과목 정보 요약
- 15주 로드맵: 2~4주 정보의 표현 → 5~11주 기계어(x86-64, GDB, 스택·제어, 프로시저, 데이터, 버퍼 오버플로) → 12~14주 최적화·캐시·링킹
- 관통 예제: 하나의 C 프로그램을 비트 → 어셈블리 → 최적화 → 캐시 → 링킹 순으로 추적

## 확인 문제
1. 50000*50000 을 32비트 int 에 못 담는 이유와 결과를 보장 못 하는 이유 → 2.5×10⁹ > 2³¹−1, signed 오버플로는 UB
2. fun(3) 이 2.0000006 인 이유 → a[3] 이 d 의 상위 4바이트 자리라서 지수·가수 비트가 바뀜
3. copyij vs copyji 19배 차이 → 행 우선 저장, 연속 접근은 캐시 공간 지역성 활용
