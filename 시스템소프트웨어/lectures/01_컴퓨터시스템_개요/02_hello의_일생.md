# 02. hello 프로그램의 일생: 컴퓨터 시스템 둘러보기 (1-2. Introduction Part 2)

> 출처: `2026-2/시스템소프트웨어/1-2. introduction_part2 (1).pdf` (CS:APP 1장)

## 한눈에 보기
> hello.c 가 **컴파일 시스템**을 거쳐 실행 파일이 되고, **버스**를 타고 디스크 → 메모리 → 레지스터 → 화면으로 옮겨 다니며, **캐시·메모리 계층** 위에서, 운영체제가 만든 **프로세스·가상 메모리·파일**이라는 착시 속에서 실행된다.

---

## 1.1 정보 = 비트 + 문맥
- 모든 정보(파일, 메모리의 프로그램·데이터, 네트워크 패킷)는 **비트의 나열**
- 같은 바이트도 **문맥**에 따라 정수·실수·문자·기계 명령어로 다르게 읽힌다
- `#include` → ASCII 35 105 110 99 108 117 100 101 (공백 32, `\n` 10)

## 1.2 컴파일 시스템 4단계 ⭐
| 단계 | 도구 | 입력 → 출력 | 하는 일 |
|---|---|---|---|
| ① 전처리 | cpp | hello.c → **hello.i** | `#include` 삽입, `#define` 치환 |
| ② 컴파일 | cc1 | hello.i → **hello.s** | C → 어셈블리(텍스트) |
| ③ 어셈블 | as | hello.s → **hello.o** | 기계어, **재배치 가능 목적 파일**(바이너리) |
| ④ 링킹 | ld | hello.o → **hello** | 다른 목적 파일·C 라이브러리(printf 등)와 결합 → 실행 파일 |

```sh
gcc -o hello hello.c   # 네 단계 모두
gcc -S hello.c         # hello.s 까지
gcc -c hello.c         # hello.o 까지
```
- hello.o 는 **직접 실행 불가** → 링킹 필요
- hello.s(사람이 읽는 텍스트) 와 hello.o(기계어 바이너리) 는 담은 명령이 같다

### 컴파일 시스템을 알아야 하는 이유
1. **성능 최적화**: switch vs if-else, 포인터 vs 배열 중 무엇이 빠른가 (12주)
2. **링크 오류 이해**: "정의되지 않은 참조", 정적/전역 변수, 정적/동적 라이브러리 (14주)
3. **보안**: 버퍼 오버플로는 스택에 데이터·제어 정보가 어떻게 놓이는지 몰라서 생긴다 (11주)

## 1.4 하드웨어 구성
| 구성 요소 | 역할 |
|---|---|
| **버스** | 구성 요소 사이 공유 통로, **워드** 단위 전송 (x86-64 는 8바이트) |
| **I/O 장치** | 키보드, 마우스, 디스플레이, 디스크. 컨트롤러/어댑터로 I/O 버스에 연결 |
| **주기억장치(DRAM)** | 실행 중 프로그램·데이터. **바이트 단위 주소**를 가진 바이트 배열 |
| **CPU** | PC(다음 명령어 주소), 레지스터 파일, ALU |

- 자료형 크기(Linux x86-64): short 2, int·float 4, long·double 8 바이트
- CPU 는 **PC 가 가리키는 명령어를 fetch → 해석 → 실행 → PC 갱신** 반복. 실행 종류: **Load**(메모리→레지스터), **Store**(레지스터→메모리), **Operate**(ALU 연산), **Jump**(PC 변경)

### ./hello 실행 3단계
1. **입력**: 키보드 → USB 컨트롤러 → I/O 버스 → I/O 브리지 → 시스템 버스 → 레지스터 → 셸이 메모리에 문자열로 저장
2. **적재**: 디스크의 hello 코드와 "hello, world\n" 을 메모리로 복사. **DMA** 로 장치가 메모리에 직접 전송 (CPU 부담 감소)
3. **출력**: CPU 가 main 명령어를 실행 → 문자열 바이트를 메모리 → 레지스터 → 그래픽 어댑터 → 화면

> 같은 데이터가 여러 번 **복사**된다 → 이 비용을 줄이는 게 캐시

## 1.5~1.6 캐시와 메모리 계층
| 저장장치 | 용량 | 지연 규모 |
|---|---|---|
| 레지스터 | 수백 B | 클럭 사이클 |
| DRAM | 수십 GB | 나노초(10⁻⁹) |
| SSD | 수 TB | 마이크로초(10⁻⁶) |
| HDD | 수 TB | 밀리초(10⁻³) |

- **캐시**: 가까운 미래에 필요할 정보를 CPU 가까이 잠시 두는 영역. L1(가장 빠름) < L2 < L3(코어 공유)
- 캐시가 통하는 이유 = **지역성**: 최근 쓴 것(**시간 지역성**)과 그 근처(**공간 지역성**)를 다시 쓴다
- **메모리 계층**: L0 레지스터 → L1~L3 캐시(SRAM) → L4 주기억장치(DRAM) → L5 SSD/HDD → L6 원격 저장소
  - 위로 갈수록 작고·빠르고·비쌈
  - **Lk 는 Lk+1 의 캐시** (주기억장치는 디스크의 캐시)

## 1.7 운영체제
- 목적: ① 잘못된 프로그램으로부터 하드웨어 보호 ② 복잡한 하드웨어를 단순·균일하게
- **세 가지 추상화**
  - **파일** ← I/O 장치
  - **가상 메모리** ← 주기억장치 + 디스크
  - **프로세스** ← 프로세서 + 메모리 + I/O
- **프로세스**: 실행 중 프로그램의 추상화, 각자 하드웨어를 독점한다고 믿음
- **문맥 전환**: 커널이 PC·레지스터 등 상태를 저장하고 다른 프로세스 상태 복원 (메모리 전체를 복사하는 건 아님)
- **스레드**: 한 프로세스 안에서 코드·데이터를 공유하는 여러 실행 흐름 (공유 쉽고 전환 가벼움)
- **가상 주소 공간**(낮은 주소 → 높은 주소): 읽기 전용 코드·데이터 → 읽기/쓰기 데이터 → 힙(malloc, 위로 성장) → 공유 라이브러리 → 사용자 스택(아래로 성장) → 커널 가상 메모리
- **파일** = 바이트의 나열. 모든 I/O 장치를 파일로 다룸 (Unix I/O)

## 1.8~1.9 네트워크와 주요 주제
- 네트워크 = 또 하나의 I/O 장치. ssh 로 서버에서 ./hello 실행 = 클라이언트 → 서버 셸 → 실행 → 출력 전송 → 내 화면
### Amdahl 의 법칙 ⭐
개선 비율 α, 그 부분 속도 향상 k 일 때 전체 속도 향상
```
S = 1 / ((1 − α) + α / k)
```
- 예: α = 0.6, k = 3 → S = 1 / (0.4 + 0.2) ≈ **1.67배** (100초 → 60초)
- 한계(k → ∞): S_max = 1 / (1 − α) = **2.5배** → 개선 안 한 부분이 상한을 정한다
### 동시성 vs 병렬성
- **동시성**: 여러 작업이 시간상 겹쳐 진행 / **병렬성**: 실제로 동시에 실행
- 수준: 스레드 수준(멀티코어), 명령어 수준 ILP(파이프라인, 슈퍼스칼라), SIMD(명령 하나로 여러 데이터)
- 추상화: 파일, 가상 메모리, 프로세스, **ISA**(프로세서 회로의 추상화), 가상 머신(컴퓨터 전체)

## 생각해 볼 것
- 폰 노이만 구조(명령어·데이터가 같은 메모리) vs 하버드 구조(명령어·데이터 메모리 분리) → 위 구성도는 폰 노이만 쪽
