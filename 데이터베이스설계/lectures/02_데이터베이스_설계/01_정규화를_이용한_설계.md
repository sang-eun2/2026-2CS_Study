# 01. 정규화를 이용한 데이터베이스 설계 (Part 1: Database Design Using Normalization)

> 출처: `2026-2/데이터베이스설계/01. Database Design Using Normalization.pdf` (Kroenke & Auer, *Database Processing* 14판)

## 한눈에 보기
> 상황: 기존 데이터(테이블)를 받았다. **그대로 저장할까, 변형해서 저장할까?** → 답은 DB 의 용도에 달렸다.

| DB 종류 | 설계 방향 | 이유 |
|---|---|---|
| **갱신 가능 DB** (운영 DB) | **정규화** (보통 BCNF, 다치 종속은 4NF) | 수정 이상(anomaly)·불일치 방지 |
| **읽기 전용 DB** (BI, 데이터 웨어하우스) | **비정규화** 허용 | 조인 없이 빠른 조회가 더 중요 |

---

## 1. 받은 테이블 구조 평가하기
```sql
SELECT COUNT(*) AS NumRows FROM SKU_DATA;          -- 행 수
SELECT TOP 10 * FROM SKU_DATA;                      -- 열 구성 (SQL Server; Oracle 은 FETCH FIRST 10 ROWS ONLY)
```
- 키 후보, 함수 종속성, 널 여부, **외래키 가정이 맞는지** 확인
```sql
-- SKU_DATA.Buyer 가 BUYER.Buyer 에 반드시 있어야 한다는 가정 검사
SELECT Buyer FROM SKU_DATA
WHERE Buyer NOT IN (SELECT Buyer FROM BUYER);       -- 결과가 비어 있으면 위반 없음
```

## 2. 갱신 가능 DB: 정규화
| 정규화 | 장점 | 단점 |
|---|---|---|
| | 수정 이상 제거, 중복 감소, 일관성 | 조인이 늘어 처리 시간 증가, 프로그래밍 복잡 |

- 예: 비정규 EQUIPMENT_REPAIR → **ITEM** 과 **REPAIR** 로 분해
- 분해 후 마무리: `INSERT INTO 새테이블 SELECT ...` 로 데이터 복사 → `DROP TABLE` 로 옛 테이블 제거 → `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` 로 참조 무결성

### BCNF 를 일부러 안 쓰는 경우: 우편번호
- CUSTOMER(CustomerID, Name, Street, City, State, **ZIP**): ZIP → (City, State) 이지만 ZIP 은 후보키가 아님 → BCNF 위반
- 그래도 분해하지 않는 이유: ZIP 은 거의 안 바뀌고, 이상이 생겨도 업무에서 잡히며, 조인을 안 하는 편이 빠르다
- 반면 **다치 종속(multivalued dependency)** 은 이상이 심각 → **항상 별도 테이블(4NF)**

## 3. 읽기 전용 DB: 비정규화
- 운영 DB 에서 추출한 비운영 DB, 질의·보고·데이터 마이닝용. 운영 의미의 갱신은 없음 (주기적으로 새 데이터만 적재)
- **비정규화** = 정규화된 테이블을 **미리 조인**해 비정규 테이블로 저장
- **맞춤 테이블**: 같은 데이터를 용도별로 여러 벌 복사 (예: PRODUCT 를 가격 조회용, 재고용 등으로)

## 4. 흔한 설계 문제 4가지 ⭐
| 문제 | 예 | 해결 |
|---|---|---|
| **다값·다열 문제** | EMPLOYEE(…, Child1, Child2, Child3) | 다값 속성을 **별도 테이블**로 (4NF 와 같은 해법) |
| **불일치 값** | 'Corn, Large Can' / 'Can, Corn, Large', Coffee / Cofee | 참조 무결성 검사, `GROUP BY` 로 의심 값 찾기 |
| **누락 값 (NULL)** | | `IS NULL` 로 확인, 의미 구분 필요 |
| **범용 비고 열** | Remarks, Comments, Notes | 비고에 숨은 정보(외래키 등)를 정식 열·테이블로 |

### 다값·다열 문제
```sql
-- 자식 이름이 Gretchen 인 직원: 열이 3개면 3번 비교해야 함
SELECT * FROM EMPLOYEE
WHERE ChildName1 = 'Gretchen' OR ChildName2 = 'Gretchen' OR ChildName3 = 'Gretchen';

-- 분리 후: EMPLOYEE(EmployeeNumber, …), CHILD(EmployeeNumber, ChildName)
SELECT * FROM EMPLOYEE
WHERE EmployeeNumber IN (SELECT EmployeeNumber FROM CHILD WHERE ChildName = 'Gretchen');
```
→ 자식 수 제한이 없어지고, 자식 없는 직원의 빈 칸도 사라진다

### NULL 의 세 가지 의미 (모호함)
1. **값이 부적절**: 남성의 DateOfLastChildbirth
2. **적절하지만 모름**: 여성인데 날짜를 모름
3. **적절하고 알지만 입력 안 됨**
