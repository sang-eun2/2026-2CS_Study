# 02. E-R 모델을 이용한 데이터 모델링 (Part 2: Data Modeling with the E-R Model)

> 출처: `2026-2/데이터베이스설계/02. Data Modeling with the Entity-Relationship Model.pdf`

## 한눈에 보기
> **데이터 모델** = DB 설계의 청사진. 설계보다 추상적이라 **바꾸기 쉬움** → 개념적 문제를 여기서 해결한다.
> 설계 2단계: **데이터 모델링(개념 설계, 요구 분석 단계)** → **DB 설계(논리 + 일부 물리 설계)**

| 개념 | 요점 |
|---|---|
| 개체(Entity) | 사용자가 추적하려는 것. 클래스(종류) vs 인스턴스(하나) |
| 속성(Attribute) | 개체의 특성 |
| 식별자(Identifier) | 인스턴스를 구별하는 속성 → 설계에서 **키**가 됨 |
| 관계(Relationship) | 개체 간 연관. 차수(degree), 카디널리티 |
| 약한 개체 / ID 종속 | 다른 개체에 존재가 / 식별자가 종속 |
| 서브타입 | IS-A, 배타/포함, 부분/전체 |

## 1. E-R 모델의 종류
| 버전 | 특징 |
|---|---|
| 원래 E-R (Peter Chen, 1976) | |
| 확장 E-R | 서브타입 추가 |
| **IE (Information Engineering, James Martin 1990)** | **까마귀발(crow's foot)** 표기, 이해 쉬움 → **이 수업에서 사용** |
| IDEF1X | 미국 NIST 표준 (ER-Win 이 지원) |
| UML | 객체지향 (OMG) |

## 2. 개체, 속성, 식별자
- 개체 클래스(CUSTOMER) ↔ 개체 인스턴스(특정 고객). 같은 클래스는 같은 속성, 값만 다름
- 속성은 예전엔 타원, 요즘은 사각형 안에 나열
- **복합 식별자**: 둘 이상 속성으로 구성
- 용어 짝: **개체 – 식별자** (모델) / **테이블 – 키** (설계)

## 3. 관계
- **차수**: 참여 개체 수 — 2개 = **이항(binary)**, 3개 = **삼항(ternary)**
- 개체와 테이블의 핵심 차이: 개체 간 관계는 **외래키 없이** 표현 가능 → 초기 설계에 유리
- 오늘날 관계에는 속성을 붙이지 않음

### 카디널리티 ⭐
| | 의미 | 종류 |
|---|---|---|
| **최대** | 참여할 수 있는 최대 인스턴스 수 | 1:1, 1:N, N:M |
| **최소** | 반드시 참여해야 하는 최소 수 | 0 = **선택(optional)**, 1 = **필수(mandatory)** |

- 1:N 에서 1 쪽 = **부모**, N 쪽 = **자식** (EMPLOYEE 1 : N COMPUTER)
- 이런 관계 = **HAS-A** 관계
- IE 표기 읽기: 해당 개체 **쪽 끝을 본다** — **타원(○) = 0(선택)**, **세로줄(|) = 1(필수)**, 까마귀발 = 다(many)

## 4. 약한 개체와 ID 종속 개체
| | 정의 | 예 |
|---|---|---|
| **ID 종속 개체** | 식별자에 **부모의 식별자가 포함**된 자식 | BUILDING : APARTMENT, PAINTING : PRINT |
| **약한 개체** | **존재**가 다른 개체에 종속 | 모든 ID 종속 개체는 약한 개체 |
| 비ID 종속 약한 개체 | 존재는 종속이지만 식별자에 부모 식별자 없음 | |

- ID 종속 개체 → 부모로의 최소 카디널리티는 **항상 1**
- **식별 관계(identifying)**: ID 종속 개체와 부모 — **실선**
- **비식별 관계(nonidentifying)**: 강한 개체끼리, 또는 비ID 종속 약한 개체 — **점선**

## 5. 서브타입
- 슈퍼타입(STUDENT)의 특수한 경우(UNDERGRADUATE, GRADUATE). 공통 속성은 슈퍼, 고유 속성은 서브
- **판별자(discriminator)**: 어느 서브타입인지 나타내는 속성
| 구분 | 의미 |
|---|---|
| **배타(exclusive)** | 슈퍼 하나가 **최대 하나**의 서브와 관계 |
| **포함(inclusive)** | 하나 이상의 서브와 관계 가능 |
| **전체(total)** | 반드시 어느 서브에 속함 |
| **부분(partial)** | 어느 서브에도 안 속해도 됨 |
- **IS-A 관계**: 서브타입 = 슈퍼타입. **식별자가 동일**
- 목적: **값이 부적절한 NULL** 을 피하려고

## 6. 모델링 패턴
| 패턴 | 설명 | 예 |
|---|---|---|
| 강한 개체 1:1, 1:N, N:M | 독립적인 개체 간 관계 | |
| **연관(association) 패턴** | N:M 관계에 **추가 속성**이 있으면 두 부모에 ID 종속인 **연관 개체** | QUOTATION(CompanyName, PartNumber, **Price**) |
| **다값 속성 패턴** | 다값 속성을 ID 종속 개체로 분리 (복합 다값 속성도) | 회사의 여러 전화번호 |
| **원형/인스턴스(archetype/instance)** | 추상적 부모의 물리적 구현이 자식 | PAINTING:PRINT, CLASS:SECTION, YACHT_DESIGN:YACHT, HOUSE_MODEL:HOUSE |
| **라인 아이템(line-item)** | 주문 – 주문 항목(ID 종속) – 상품(강한 개체) | SALES_ORDER : LINE_ITEM : ITEM |
| 기타 혼합 | 다값 복합 그룹의 원소 하나가 다른 강한 개체의 식별자 | RECIPE – INGREDIENT_USE – INGREDIENT, EMPLOYEE – EMPLOYEE_SKILL – SKILL |
| **for-use-by** | 서브타입처럼 보이지만 용도별로 쓰이는 개체 | |
| **재귀(recursive)** | 개체가 자기 자신과 관계 (1:1, 1:N, N:M) | 직원–관리자 |

## 7. 모델링 과정은 반복적이다 (Highline University 예)
- 대학의 단과대, 학과, 교수, 학생을 추적하는 DB
- **보고서·양식을 하나씩 분석**하며 모델을 고쳐 나감: College Report → 1차 모델 → Department Report → 2차 → Department Student Report → 3차 → 합격 통지서 → 4차 → 최종
> 요구사항 문서마다 새 개체·관계·카디널리티가 드러나므로, 모델은 한 번에 완성되지 않는다
