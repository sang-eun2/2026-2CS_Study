# 03. 데이터 모델을 데이터베이스 설계로 변환 (Part 3: Transforming Data Models into Database Designs)

> 출처: `2026-2/데이터베이스설계/03. Transforming Data Models into Database Designs.pdf`

## 한눈에 보기
> **DB 설계** = 특정 DBMS 에서 실제로 구현할 수 있는 명세 (논리 설계 + 일부 물리 설계(데이터 타입)). SDLC 의 컴포넌트 설계 단계.

### 변환 3단계
1. **개체마다 테이블 생성**: 기본키 선택, 대체키 지정, 열 속성(널, 타입, 기본값, 제약) 지정, 정규화 확인(BCNF/4NF)
2. **관계 생성**: 외래키 배치 (1:1, 1:N, N:M, ID 종속, 서브타입, 재귀, 삼항)
3. **최소 카디널리티 강제**: 참조 무결성 동작, 트리거

---

## 1. 테이블 만들기
### 기본키
- 이상적인 기본키 = **짧고, 숫자이고, 변하지 않는** 값
- **대리키(surrogate key)**: 이상적 조건을 만족하는 인위적 키 (DBMS 가 자동 생성). 사용자에게 의미는 없음

### 후보키(대체키)
- 행을 유일하게 식별하는 다른 키. 표기 **AKn.m** (n 번째 대체키의 m 번째 열)

### 열 속성
- **널 여부**, **데이터 타입**(Char(n), Varchar(n), Date, Time, Integer, Decimal(m,n), Numeric(m,n), Money(m,n) 등 — SQL Server·Oracle·MySQL 마다 다름), **기본값**
- **데이터 제약** 4종
| 제약 | 의미 |
|---|---|
| 도메인 | 값이 정해진 집합 안에 |
| 범위 | 값이 범위 안에 |
| 관계 내(intrarelation) | **같은 테이블** 다른 열과 비교 (예: 출생 < 사망) |
| 관계 간(interrelation) | **다른 테이블** 값과 비교 = 외래키 참조 무결성 |

## 2. 관계 표현 ⭐
| 관계 | 변환 방법 |
|---|---|
| **1:1 강한 개체** | 한쪽의 기본키를 다른 쪽에 외래키로 (어느 쪽이든 가능, 최소 카디널리티 고려 — O-M 과 M-O 에서 선호 설계가 다름) |
| **1:N 강한 개체** | **부모(1)의 키를 자식(N)에 외래키로** ("부모 키를 자식에 넣는다") |
| **N:M 강한 개체** | 외래키 둘 곳이 없음 → **교차 테이블(intersection table)**: 양쪽 기본키로만 구성된 복합 기본키, 각각 외래키. 예 `COMPANY_PART_INT(CompanyName, PartNumber)` |
| **연관 관계** | 교차 테이블 + **추가 속성** = **연관 테이블**. 예 `QUOTATION(CompanyName, PartNumber, Price)` |
| 다값 속성 | ID 종속 테이블 (부모 키 + 값이 복합 기본키) |
| 원형/인스턴스 | ID 종속이면 부모 키가 자식 기본키의 일부, 약한 비ID 종속이면 외래키만 |
| 서브타입 | 슈퍼타입 키를 서브타입의 **기본키이자 외래키**로 |
| 재귀 1:1, 1:N | 같은 테이블 안에 자기 테이블을 참조하는 외래키 |
| 재귀 N:M | 자기 자신과의 교차 테이블 |

### 삼항 이상 관계의 제약
| 제약 | 의미 |
|---|---|
| **MUST** | 한 개체가 반드시 특정 다른 개체와 함께 나타나야 함 |
| **MUST NOT** | 특정 두 개체 조합이 나타나면 안 됨 |
| **MUST COVER** | 이항 관계가 정한 모든 조합이 삼항 관계에 나타나야 함 |

## 3. 최소 카디널리티 강제
| 유형 | 의미 (부모-자식) | DBMS 지원 |
|---|---|---|
| **O-O** | 둘 다 선택 | 할 일 없음 |
| **M-O** | **부모 필수**, 자식 선택 | 참조 무결성 + **외래키 NOT NULL** 이면 DBMS 가 강제 |
| **O-M** | 부모 선택, **자식 필수** | DBMS 도움 거의 없음 → **트리거** 필요 |
| **M-M** | 둘 다 필수 | 위 둘을 동시에 → 가장 어려움, 신중한 프로그래밍 |

### 연쇄 갱신·삭제
- **연쇄 갱신**: 부모 기본키 변경을 자식 외래키에 반영. **대리키는 안 바뀌므로 불필요**
- **연쇄 삭제**: 부모 삭제 시 자식도 삭제. **강한 개체는 보통 안 함, 약한 개체는 보통 함**

### DEPARTMENT(부모) – EMPLOYEE(자식) 예
**M-O (부모 필수)**
- 부모: 생성 가능 / 기본키는 대리키 아니면 연쇄 갱신 / 삭제 시 직원도 지울지 결정 (예 → 연쇄 삭제, 아니오 → 직원 있으면 금지)
- 자식: 참조 무결성 + 외래키 NOT NULL → 새 직원은 유효한 부서 필요, 부서 변경도 유효해야 함 / 직원 삭제는 자유

**O-M (자식 필수)**
- 부모: 생성하려면 자식 관계를 함께 만들어야 → **트리거**, 기본키 변경도 자식 하나 이상 함께 → **트리거** / 부서 삭제는 가능
- 자식: 삽입 자유 / **그 부서의 마지막 직원**이면 부서 변경·삭제 불가

**M-M**: 위 규칙이 서로 충돌 (새 부서 트리거가 직원을 만들려 하는데 직원은 유효한 부서를 먼저 요구 / 마지막 직원 삭제 금지 때문에 부서를 못 지움)

### 트리거
- 지정한 테이블·뷰에 지정한 **이벤트가 일어날 때 DBMS 가 실행하는 저장 프로그램**. DBMS 가 기본으로 못 하는 최소 카디널리티 동작을 강제할 때 사용

### 문서화
- 필수 부모(M-O)는 설계 도구로 표시 가능 / 필수 자식(O-M)은 **글로 된 문서**(Figure 3-29(b) 양식) 필요
