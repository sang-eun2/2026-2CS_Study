## 1. 트랜잭션
- **트랜잭션(LUW, 논리적 작업 단위)**: DB 에 대한 일련의 동작을 **원자적 단위**로 — 전부 실행되거나 하나도 안 됨
  - 예: 고객 잔고 갱신·주문 추가·재고 차감 중 하나가 실패하면 모두 취소해야 불일치가 없다
- **동시 트랜잭션**: 사용자에겐 동시에 처리되는 것처럼 보이지만 CPU 는 **번갈아(interleave)** 실행
- 동시성 문제: **갱신 손실(lost update)**, **불일치 읽기(inconsistent read)**

### 갱신 손실
- 사용자 A, B 가 같은 재고(10)를 읽음 → A 가 5 빼서 5 저장 → B 가 3 빼서 7 저장 → **A 의 갱신이 사라짐**

## 2. 잠금 (Resource Locking)
- 레코드를 바꾸려 할 때 다른 응용이 같은 레코드 사본을 얻지 못하게
| 용어 | 의미 |
|---|---|
| **암시적 잠금** | DBMS 가 거는 잠금 |
| **명시적 잠금** | 응용 프로그램이 거는 잠금 |
| **잠금 단위(granularity)** | 행, 페이지, 테이블, DB. **클수록 관리 쉽지만 충돌 잦음** |
| **배타 잠금(exclusive)** | 다른 사용자는 **읽기도** 불가 |
| **공유 잠금(shared)** | 다른 사용자는 읽기 가능, **갱신 불가** |

### 직렬 가능 (Serializable)
- 동시에 실행했는데 **따로 실행한 것과 같은 결과**
- **2단계 잠금(two-phased locking)**: **확장 단계**(필요한 잠금을 얻음) → 첫 잠금을 풀면 **축소 단계**(더는 잠금을 못 얻음)
- 특수형: 트랜잭션 내내 잠금을 얻고 **COMMIT/ROLLBACK 까지 하나도 안 풂** → 더 제한적이지만 구현이 쉬움

### 교착 상태 (Deadlock, deadly embrace)
- 두 트랜잭션이 **서로 상대가 가진 자원을 기다림**
- **예방**: 필요한 잠금을 **한 번에** 요청 / 모든 프로그램이 **같은 순서로** 잠금
- **해소**: DBMS 가 탐지 알고리즘으로 찾아 **한 트랜잭션을 중단하고 롤백**

### 낙관적 vs 비관적 잠금
| | 낙관적 (optimistic) | 비관적 (pessimistic) |
|---|---|---|
| 가정 | 충돌이 **없을** 것 | 충돌이 **있을** 것 |
| 방식 | 처리 후 충돌 여부 확인 → 있으면 **다시 실행** | 처리 **전에 잠금** → 처리 후 해제 |
| 적합 | **인터넷**, 많은 인트라넷 응용 | 충돌이 잦은 환경 |

### 잠금 특성 선언
- 대부분의 응용은 잠금을 직접 걸지 않고 **트랜잭션 경계**와 원하는 잠금 동작만 선언 → 바꿀 때 선언만 고치면 됨
- `BEGIN TRANSACTION` / `COMMIT TRANSACTION` / `ROLLBACK TRANSACTION` (DBMS 마다 문법 다름)
- **SQL Server, MySQL 은 자동(암시적) COMMIT**, **Oracle 은 명시적 COMMIT 필요**

## 3. ACID ⭐
| | 의미 |
|---|---|
| **A**tomic | 전부 실행되거나 하나도 안 됨 |
| **C**onsistent | **문장 수준**: 각 SQL 문이 처리하는 행을 일관되게 / **트랜잭션 수준**: 트랜잭션 동안 관련 행 전체를 보호 (자기 변경을 못 볼 수도 있음) |
| **I**solated | 프로그래머가 **격리 수준**을 선언하면 DBMS 가 잠금으로 보장 |
| **D**urable | 커밋된 변경은 **영구적** |

### 읽기 문제와 SQL-92 격리 수준
| 읽기 문제 | 의미 |
|---|---|
| **더티 읽기** | 커밋되지 않은 변경을 읽음 |
| **반복 불가능 읽기** | 같은 행을 다시 읽었더니 (다른 트랜잭션의 수정·삭제로) 값이 달라짐 |
| **팬텀 읽기** | 다시 읽었더니 (다른 트랜잭션의 삽입으로) 새 행이 나타남 |

| 격리 수준 | 더티 | 반복 불가능 | 팬텀 |
|---|---|---|---|
| Read Uncommitted | 가능 | 가능 | 가능 |
| Read Committed | 방지 | 가능 | 가능 |
| Repeatable Read | 방지 | 방지 | 가능 |
| **Serializable** | 방지 | 방지 | 방지 |
> 격리 수준이 높을수록 안전하지만 처리량이 줄어든다

### 커서 종류
- **커서** = 레코드 집합을 가리키는 포인터 (SELECT 로 정의)
| 종류 | 특징 |
|---|---|
| Forward only | 앞으로만 이동 |
| Static (스크롤) | 커서를 열 때의 **스냅샷** 처리 |
| Keyset (스크롤) | Static 과 Dynamic 의 일부 특징 결합 |
| Dynamic (스크롤) | 모든 기능 (다른 사용자 변경도 보임) |
> 적절한 격리 수준과 커서 타입 선택은 DB 설계에서 중요

## 4. 보안
- 보안 = **인가된 사용자만, 인가된 작업을, 인가된 시간에**
- 개발: 사용자별 처리 권한·책임 결정 → DBMS 와 응용의 보안 기능으로 강제
- DBMS 보안: 사용자·그룹(**역할**)별로 객체 작업 제한, 사용자명·비밀번호
- DCL: `GRANT` / `REVOKE`

### DBMS 보안 지침 (요약)
- 방화벽 뒤에서 운영하되 **뚫렸다고 가정**하고 계획
- 최신 OS·DBMS 패치, **최소 기능·최소 프로토콜**, 불필요한 시스템 저장 프로시저 삭제
- **기본 로그인·게스트 비활성화**, 대화식 로그온 제한
- DBMS 컴퓨터 물리 보안 (잠긴 방, 출입 기록, 그 컴퓨터에서 작업 금지)
- 계정: DBMS 서비스는 **저권한 계정**, 강한 비밀번호, 실패 로그인 모니터링, 역할 멤버십 점검, null 비밀번호 감사, **최소 권한**, DBA 권한 제한
- 보안 계획과 비상 절차를 만들고 연습

### 응용 보안
- DBMS 보안이 부족할 때 응용 코드로 보완 (인터넷 응용은 웹 서버에서)
- 그래도 **DBMS 보안을 먼저**: 데이터에 가까울수록 침투 가능성이 낮고, 빠르고 싸고 품질이 좋다

### SQL 인젝션
- 사용자 입력이 **SQL 문을 바꿔 버리는** 공격
- 예: 이름 입력란에 `'Benjamin Franklin' OR TRUE` → `WHERE Name = 'Benjamin Franklin' OR TRUE` 가 되어 **모든 행** 반환
- 방어: 입력을 철저히 검사해 추가 SQL 문법이 없는지 확인 (실무에선 **PreparedStatement 같은 매개변수 바인딩** 사용 — 05_어플리케이션_프로그래밍 참고)

## 5. 복구
| 방식 | 내용 | 문제 |
|---|---|---|
| **재처리(reprocessing)** | 알려진 시점(저장본)으로 돌아가 그 뒤 작업을 다시 처리 | 바쁜 시스템은 **따라잡지 못함**, 비동기 이벤트로 결과가 달라질 수 있음 → 비현실적 |
| **롤백/롤포워드** | 주기적 저장 + 그 이후 **변경 로그**(시간순) 유지 | 표준 방식 |

- **롤백**: 잘못된 변경을 **되돌림** → **이전 이미지(before-image)** 사용 → 유효한 트랜잭션 재처리
- **롤포워드**: 저장본을 복원하고 그 이후 유효한 트랜잭션을 **다시 적용** → **이후 이미지(after-image)** 사용
- **체크포인트**: DB 와 로그의 **동기화 지점**. DBMS 가 새 요청을 받지 않고, 진행 중 요청을 끝내고, 버퍼를 디스크에 쓴 뒤 완료를 기다림 → 복구 시 **마지막 체크포인트 이후** after-image 만 적용하면 돼 **복구가 빨라짐**. 시간당 여러 번, 대부분 자동

## 6. DBA 의 책임
- 구조 관리(설계 변경·문서화), 동시성 제어, 보안, 백업·복구, DBMS 관리(성능, 버전), 데이터 저장소(메타데이터) 관리 등
